# 架构与三代优化（R1/R2/R3C）——读代码前先读这个

## 顶层数据流（ae_top → ae_core）

加速器只有一个任务：吃编译器（12_actv/a3/compiler_a3.py）吐出的描述符流（seq.mem，256 位一条），逐条执行。描述符有八类 op：GEMM（0/1/2）、COPY（3，B 矩阵重驻留）、LOAD_W（4）、LOAD_CTX（5）、STORE、ATTN_S（softmax+GEMM 注意力）、AE_ACTV（6，片上算子）、END（15）。

```
DDR ──DMA(读引擎/写引擎)──> CTX RAM(64 URAM, 激活驻留) + WRAM(96×BRAM, 权重驻留)
                                    │                        │
                                    └──A口──> 16×96 脉动阵列 1536 PE ──快照──> requant(24套rq_ms) ──> tile_buf ──B口写回──> CTX → STORE → DDR
                                             （softmax / copy / actv 各自的小引擎）
调度器 ae_sched：发描述符、skip 优化（PRIM 模式）、R2 预取 FSM
```

模块清单（综合 17 文件，全在 22_r3c_rtl/rtl/）：

| 模块 | 干什么 | 规模（LUT/DSP） |
|---|---|---|
| ae_pe | 单个乘加单元：int8×int8 累加 + 27 位快照 + 末脉冲链 | ×1536，1 DSP/PE |
| ae_sysarr | 16×96 阵列：边缘偏斜（行 i 延 i 拍、列 j 延 j 拍）、快照侧读出 | （PE 之外少量胶水） |
| ae_gemm | GEMM 引擎：喂数道+读出道两段 FSM、requant 时分复用、tile_buf 双缓冲 | 65k / 1536 |
| ae_dma | 双引擎 DMA：读引擎 + 写引擎，AXI 全双工，R2 预取握手 | 2.2k |
| ae_sched | 调度：描述符发射、PRIM skip、pf FSM（TAG_CTX 预取） | 1.0k |
| ae_softmax / ae_copy / ae_actv | softmax（行级 16 并行）、COPY、片上算子（GELU/eltwise） | 10k / 15k / 25k |
| ae_requant / rq_ms / rq_v2 | 重量化：24 套 rq_ms 时分复用（4 列共享一套） | 在 u_gemm 内 |
| ae_ctx_ram / ae_dpram | CTX（URAM 16 bank）/ WRAM（96 bank BRAM） | 64 URAM / 114 BRAM |

## R1：独立写通道（DMA 双引擎）

**问题**：旧 DMA 一个 FSM 服务所有请求，读和写排队，总时间 = 算+读+写的串行和（899M 拍）。

**改法**：拆成读引擎（AR/R 通道）和写引擎（AW/W/B 通道）两条独立 FSM。AXI 本身是全双工的，以前只是自己没利用。STORE 改 fire-and-forget（不等回应继续发）。GEMM 优先用 CTX A 口，写引擎让拍。

**效果**：写完全藏进计算里（写车道 < 计算车道时免费）。原理页：21_r1r2_explain/。

## R2：CTX 预取

**问题**：读（LOAD_CTX 292M 拍）还没藏住——GEMM 算完一段要停下来等下一段的激活从 DDR 搬进来。

**改法**：调度器加 pf FSM，GEMM 喂数期间提前把下一段激活搬进 CTX 的另一个半区（bit11 选区），GEMM 一结束数据已在片上。LOAD 命中预取时直接改指针，一个字的搬运都不用做。

**效果**：总拍 899→427M，GEMM 计算占总时间 78.8%——计算第一次成为绝对主线。

**R2 的两个 bug 修史**（都有翻案过程，接手时别再走弯路）：
1. B 口仲裁静默丢预取写 → seg_0602 出 83 字节错。根因是纯优先级仲裁 + 读引擎 rready 恒真。修法：pf_ctx_stall 三步握手。17_r2fix_report/ 有完整报告。
2. pf_ctx_stall 自己又引入死锁（LOAD 命中预取时冻自己在等的预取）→ 本轮删项修复。见 STATUS.md「前置缺陷」节。

## R3C：行组流水（本轮）

**问题**：GEMM 引擎内部还是串行的——一行 16 个输出算完（喂数 k+2 拍），要等整列排空（127 拍）、量化（64 拍）、写回（wb 拍）全做完，才能喂数下一行。累加器驻留在 DSP 的 P 寄存器里，读出时不能喂数（新积会加进没读走的旧结果）。

**改法**（三个文件）：
1. **ae_pe**：每个 PE 加 27 位快照。控制器在最后一个 k 切片进阵列时打「末脉冲」，随 A 链一拍传一个 PE；脉冲到拍，该 PE 把累加器抄进快照、清零。27 位够用的证明：|acc| ≤ 127×127×2049 ≈ 33M < 2^26。
2. **ae_sysarr**：读出口从累加器切到快照侧（符号扩展回 32 位）。
3. **ae_gemm**：FSM 拆喂数道（st_f）和读出道（st_r）并行。行组周期 = max(k+2, 68+wb)——喂数和读出谁长谁定。

**效果**：GEMM 336.4M→185.2M（−45%）。对外零改动：描述符语义、调度器、DMA、R2 握手全不动，done 只是来得更早。

## 16×96 阵列选型（本轮第二件事）

1728 DSP 用满（100%）没有余量、不可移植。数据驱动选型（19_r3c_arch/pe_sizing.py）：

- 关键发现：**「减列数 +40% 拍数」是拿 108 编译的老流硬切的错误口径**。按 96 重编译后只 +5.2%（185.2 vs 176.1M），跟现状 185.3M 持平——因为 108 宽的满组只占行组 6%，窄层（≤96 列，占 73%）完全不受影响，TB 口径下读通道仍是瓶颈，端到端零变化。
- 96 胜过 100 全在结构：96=6×16（转置写回组边界永远 lane 对齐）、每 k 行恰好 12 个整拍（B 装载无残拍）、多留 64 颗 DSP。
- 代价：FF +26.9%（1536×27 位快照），换来 DSP −192、LUT −10.5%。

## 性能账的口径体系（最容易搞混的部分）

三层口径，算账时先说清楚在哪层：

| 口径 | 是什么 | 当前值 |
|---|---|---|
| TB | 芯片时钟域总拍（计算/读/写取最大 + 依赖停顿 40M） | 332.1M / 1.67 ms |
| HP64 | HP 口径（读服务按 64B/拍折算，DDR 效率模型） | 275.6M / 1.39 ms |
| 回归基准 | 22_r3c_rtl/sim 的小规模随机段实测 | GEMM 引擎 −24.2%（段小，省得少） |

全帧模型脚本 `19_r3c_arch/r3c_model.py`（可复算，校准系数 1.0514 来自 a3 账本）。**所有「−45%」是全帧模型口径，「−24%」是回归基准口径，两个都对。**
