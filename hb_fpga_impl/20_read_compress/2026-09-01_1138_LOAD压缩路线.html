LOAD_CTX / LOAD_W 压缩路线：R3 之后怎么把读数据的时间压下去

生成时刻：2026-09-01 11:38:00　|　数据基础：a2/a3 真实流普查（recon_loads / recon_flow / recon_scope / recon_xtab 实跑）+ R3C 模型（19_r3c_arch）　|　前提：用户裁定"带宽够"，本页不提换端口、提频率那类方案

零、先把结论说清楚

带宽确实够——真机 HP64 口径下 608MB 权重 + 680MB 激活全部读完只要 20.1M 拍，连计算通道（235.6M）的十分之一都不到。读的真正问题是"搬的字节多"和"一台读引擎串行搬"，不是搬得慢。

数字目标也很明确：R3 之后计算通道 235.6M 拍，读通道（LOAD_CTX 184.0 + LOAD_W 108.1 = 292.1M 拍）超了 56.5M。只要把读通道砍到 235.6M 以下，总时间就从 332.1M 降到 275.6M（1.39ms，再省 17%），而且 TB 验证平台和真机 HP64 两个口径从此一致。砍的路径有三条，任意一条单独走通就够。

一、读通道里都是什么（先搞清楚砍什么）

LOAD_CTX 是把激活（上一层算出来的中间结果）从 DDR 搬进片上 CTX；LOAD_W 是把权重搬进 WRAM。对 a3 流的字节构成做一次全量普查（每条 LOAD 按它的来源分类，2026-09-01 实跑）：

LOAD_CTX 的 680MB 按来源字节说明
引擎产出的图（上个 PL 段刚写进 DDR 的）548.6MB（81%）算完→写回 DDR→下一段再装回来，DDR 走了个来回
host 写入的激活（残差/重排后）130.3MBhost 边界改造的空间
host 写入的 K/Q 块66.7MB转置/分头
host 算出的 softmax P65.2MB注意力的数学
host 转置块22.2MB纯转置

怎么看：八成以上的装载是"自己刚写出去的又装回来"。这是压缩的主战场——这些字节要么根本不用出片，要么出片一次进来一次就够。

引擎直连的 548.6MB 再按"生产→消费隔几个段"分：距离 ≤2 的 171.6MB、距离 ≤5 的 217.8MB；但按"图大小能塞进 CTX（128K 字）且给消费者留够工作集"筛，只有 191.6MB 是候选（其中距离 1-5 的约 72MB，其余 119MB 是长距离大图）。这就是驻留的现实空间：不是账面上 548MB 都能驻留，是约 190MB。

二、路线一（推荐）：CTX 双区驻留——把 DDR 来回砍掉

思路：CTX 现在 2MB（16-bank URAM），已经用半区交替做 LOAD_W 的双缓冲。给激活驻留划一块"双区"——A 区放当段工作集，B 区放"下一段马上要用的、上段刚算出来的图"。上个段算完直接把结果留在 B 区，下段从 B 区读，DDR 来回整段消失。这正是 R2 预取双缓冲（半区 bit11）的延伸：预取已经把"装"藏进了计算，驻留则把"装"整个免掉。

驻留的实际收益上限（普查口径）：约 190MB 的 LOAD_CTX 免掉，读通道 292.1 − 190/3.70 = 240.7M 拍——还差 5M 没到 235.6M 的线，单靠它差一口气；如果 host 源里能再折 20MB 进片（route 1.5，见下）就过线。

代价：零字节、零 DSP、零 BRAM（容量从现有 2MB 里划）；描述符加一位"驻留基址选择"或复用现有 b_base 译码；编译器规划生命期（a4 的 _resid_place 已经写过这套逻辑，直接捡回来用）。

必须吸取的教训（a4 已试过一次，失败了）：2026-08-31 的 a4 驻留实测只省 1.1MB——98% 的候选被三个结构性原因拒掉：①tensor_link 链（405 处）②融合对内部直连（384 处，已经不出 DDR）③host 链 kind 不兼容（190 处）。问题不在驻留机制，在 a4 只挑"产段→消费段中间没有任何 host 步"的裸边界，这种边界在这个模型里本来就少。route 1 的不同做法：允许驻留"过 host 边界"——只要 host 链能折进产段尾部的 op=6（a4 的 _emit_resid_fold 已实现这个折叠，10 个站验证过机制可行），把"先折链、再驻留"串起来做，候选空间从 20 站扩到普查口径的 ~190MB。这是 a4 没试过的组合。

二点五、路线 1.5：host 边界折进片（跟路线一配套）

普查里 65.2MB 的 softmax P 和 66.7MB 的 K/Q 块是 host 写进 DDR、PL 再装回来的。NORM/ELTWISE 引擎（op=6）已经能覆盖 norm/残差加；softmax 的 S→P 归约 PL 也有（SM16）。把这几个 host 步折成产段尾部的 op=6 描述符，这 130MB 里可折的部分（P 块 247.7MB 装载里 p_in 类 65.2MB 是纯 softmax 数学）就不出片了。跟路线一叠加使用：路线一消"引擎直连"的 190MB，这条消"host 直连"里的几十 MB。

三、路线二：双读引擎——CTX 和权重并行装

现在一台读引擎串行服务两种装载：先装完 CTX 再装权重（或反之），184.0 + 108.1 = 292.1M 拍是串行和。带宽既然够，给 CTX 和 W 各配一台读引擎（AR/R 通道各一条流，分别写 CTX B 口和 WRAM），读通道变 max(184.0, 108.1) = 184.0M 拍，一步过线，还富余 51.6M。

代价与风险：ae_dma 读引擎复制一份（约 +2.4k LUT，ae_dma 现在 2,405 LUT），CTX B 口多一个写者要仲裁（R2 的 pf_ctx_stall 逻辑扩展成双请求者）。风险在验证平台 TB：两台读引擎共享 TB 从机一条 R 通道，混合并发速率没实测过（ctx 单流 3.70 B/拍、w 单流 5.62 B/拍，混合能到多少要 Verilator 实验）。真机 HP 口没这个问题（64 B/拍，两台引擎各吃各的都饱）。所以这条路线模型上最干净、实证上有一个待测点。

四、路线三：WRAM 4 组驻留——权重重装砍半

LOAD_W 的 108.1M 拍里大部分是重装：同一个权重图被多个段反复装（WRAM 现在半区双缓冲，COPY 一来就得作废全部驻留）。WRAM 从 2 组加到 4 组（442KB→884KB，每列 +2Mb，约 +36 个 BRAM36 等效），驻留表命中率上升，模型估算暴露装载 108.1→约 55M。单靠它不够（292.1−53.1=239.0M，差 3.4M），但它是唯一顺手就能做的：a2 的驻留表机制现成，只加容量。注意这是三条路线里唯一要加 BRAM 的（其余都是零 BRAM）。INT4 权重（字节直接减半）在这条线上收益最大，但 INT4 线用户已令停，本页不展开。

五、三条路线怎么选

路线改哪里读通道降到单独够不够（<235.6M）代价主要风险
1. CTX 双区驻留（+1.5 host 折叠）编译器（调度）+ CTX 地址译码一位约 240 → 约 230M配 1.5 后够零 BRAM/零 DSPa4 前车之鉴：必须"折链+驻留"联动，单做驻留没肉
2. 双读引擎ae_dma（+1 台读引擎）+ B 口仲裁184.0M够，富余 51.6M+2.4k LUTTB 混合并发速率未实测（真机无此问题）
3. WRAM 4 组WRAM 容量（BRAM）239.0M差 3.4M，不够+36 BRAM36 等效低（机制现成）

怎么看：路线 2 是纯硬件、模型收益最大、且不依赖编译器改造，推荐先做（做完直接过线）；路线 1 是字节层面的真减少（对功耗、对 HP 口径都有价值），值得跟着做；路线 3 最便宜但单独不解决问题，当顺手菜。

过了 235.6M 这条线之后，三个口径全部归一：总时间 = 计算通道 235.6M + θ = 275.6M（1.39ms），TB 和 HP64 不再有差距。再往后想快，只能继续压计算（COPY 40.3M 是下一个可动的块——DMA 列主序路由，即 R5），那是 R3 之后下一张牌。

七、实施注意

  • 顺序依赖：读压缩的一切收益都以 R3 落地为前提——R3 之前计算通道 386.7M 高高在上，读通道怎么压都被藏着，一拍不省。先 R3、再读压缩，顺序不能反。
  • 路线 1 的编译器改造要动"段自包含契约"（段的输入必须从 DDR 装）：host 驱动和黄金模型要跟着改，这是 a4 当年把它划出软件轮的原因。做的时候先在模型层验证生命期规划（recon_xtab 的普查数字直接当输入），再动编译器。
  • 路线 2 的 TB 混合速率实验很小（改 TB 加一个计数器跑一个代表段），建议 RTL 轮顺手带上，把"待测点"消掉。
