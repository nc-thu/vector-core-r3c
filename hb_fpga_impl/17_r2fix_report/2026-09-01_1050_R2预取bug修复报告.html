R2 预取写冲突 bug 修复报告

生成时刻：2026-09-01 10:50:00　|　修复完成时刻：2026-09-01 10:4x　|　改动范围：rtl/ae_dma.sv、rtl/ae_core.sv（14_rtl_r1r2）

一、问题是什么

2026-09-01 凌晨的 Verilator 门发现：seg_0602（k=257 的长 GEMM 段）在预取开启（PF=1）时， STORE 输出区有 83 个字节出错，误差 ±1 LSB；同一段关掉预取（PF=0）则逐位一致。 也就是说这不是数值计算错误，而是预取与长写回窗口抢总线时的数据通路 bug。短段（k=9/64）不触发。

二、根因（iverilog 探针实证，不是推测）

最初怀疑的 gemm_wb_active 让拍逻辑其实是个"死门"——它挡不住任何冲突。真正的问题出在两处：

  1. CTX B 口的仲裁只分优先级、不回压。后台预取往 CTX 写数据时，如果 GEMM / softmax / ACTV / 前台 LOAD 正在用 B 口，预取的写会被多路选择器直接丢掉，没有任何人知道。
  2. DMA 读引擎不知道写被丢了。它的 rready 恒为真，地址照常往前推，读完成信号照常发出。 调度器收到"预取完成"就认为数据已经到位，后续 LOAD 直接命中预取、跳过装载—— 实际 CTX 里是残缺或旧数据，错误最终在 STORE 区暴露。

探针证据：测试平台加了丢写计数器，修复前 pf_ctx_drop_cnt=7（写确实在丢），修复后 =0。

为什么只有 seg_0602 触发：k=257 的长 GEMM 喂入要 257 拍、写回窗口更长，把预取发射窗口撑得很大， 2048 字节的预取突发撞上引擎占口的概率随之上升；短段窗口小，撞上了也多半不落在 STORE 的源数据区。

三、修法（最小改动，两个文件）

  • rtl/ae_dma.sv：新增输入 pf_ctx_stall、输出 rd_tag_o（当前锁存的 tag）。 读引擎在 R_R 状态的全部动作挂在 rvalid && rready 下，而 rready = (rd_st==R_R) && !pf_ctx_stall——stall 拉高时字节数、剩余长度、CTX 写使能全部冻结， 状态机零改动，AXI 读通道自然背压。
  • rtl/ae_core.sv：计算 pf_ctx_stall = bg_wran && (rd_tag_o==CTX) && (B 口本拍被引擎占用)， 即"后台 CTX 预取在飞、且本拍 B 口选了别的引擎"时拉高，让 DMA 停下来等 B 口让出。 引擎是串行 one-hot 的，B 口必然会让出——写一个不丢。

四、验证门（全部通过）

多出的 349 个 LUT 主要落在 u_dma——rready 让拍门控扇进了写数据/写使能路径。远低于 R1 的 +2,200 预算， 时序零恶化。

五、修复后的收益确认

seg_0602 开预取现在既正确又省拍：51,094 拍 vs 关预取的 53,350 拍，净省 2,256 拍（−4.2%）。 至此 R1+R2（427.2M / 2.15ms / GEMM 78.9%）的 RTL 落地验证闭环完成：模型预测、综合、位精确仿真三者对上。

状态汇总（截至本报告）：架构线 GEMM 主线达成且硬件实证闭环——R1 独立写通道三段位精确 + 重叠可见（45.5%）， R2 预取修复后全段位精确。累计优化 1216.5M → 427.2M（−64.9%），GEMM 时间占比 28.5% → 78.9%。 下一轮可选：R3 行组流水（427 → ~297M，GEMM ~88%）。
