一、这轮做了什么（结论先行）
------------------------------------------------------------------------------
目标原本有两块：①CTX 跨段驻留（消 a2 的 1612 个无 host 步边界）、
②norm/actv host 算子融合上片（发射 op=6 描述符给 AE_ACTV 引擎）。
拍数目标 ~600M 量级、GEMM 占比 >50%。

实际交付：
  * ②做到了 actv 部分：192 个融合站点（182 个 actv 链 + 10 个 S2 恒等
    重标定链），软件全流数值与 a2 逐字节一致（192/192 站 A/B 门全过）。
  * ①和 norm 部分：结构上不可行，0 站。根因见第四节，不是实现偷懒。
  * 拍数：986.7M → 899.4M，降 87.3M（-8.8%）。GEMM 占比 34.1% → 37.4%，
    没到 >50% 的目标。差距的根源是边界账虚高：1612 个边界里真正能融合
    的只有 192 个，其余都是注意力消费者/结构不配（第四节展开）。

一句话：融合机制本身是对的、数值门全过；但这个模型里「GEMM → 激活 →
GEMM」这种理想夹心只有 192 处，消掉的 DDR 往返只占 a2 总账的一成，所以
总量下不去 600M。

三、门的执行结果（全部如实，含修过的门自身 bug）
------------------------------------------------------------------------------
1. 数值 A/B 门（ab_gate.py，2026-08-31 19:41 全过）
   每个融合站点同一份合成 A_p 走两条路：
     a2 路 = a2 的 p 段 → torch 复刻 host 链（与 host_driver 同实现：
             fp32×so → 模块前向 → clamp(round/sa)）→ 注进 a2 的 c 段
     a3 路 = a3 融合段（p GEMM → op=6 ACTV 原地查表 → c GEMM）
   判据：Y_c 逐字节相等。
   结果：192/192 站 Y_c 差 = 0，逐字节一致（含 10 个 S2 恒等链）。
   注：本机没有 batch_sXXX.pt / fp32_ref（端到端全流要在服务器跑），
   所以门是逐站点合成输入做的；每个站点的两条路覆盖该站点全部行块。

   过程中发现并修掉的三个 bug 全在门自身，编译器没错：
   a) const:N 输入条目被我填了随机字节。这类条目是 _const_stripe 的常数
      列来源，正确填法是 cval 复制满 16 lane（host_driver.py:234 同款）。
      修复后 seg_0159 一类站点立刻全对。
   b) 非增广 c 的 A 尾列没补。GEMM 条目 k 恒为 k_data+1，act_image 对一切
      这种条目都补常数列；漏补会让打包图按 k_data 步长错位——第 0 行组
      恰好重合、后续组整体移 16B，表现为 row16 起全错（backbone.stages.3
      和 feature_enhancer 的 8 个站点就是这么假 FAIL 的）。非增广时 W 末
      行恒为 0（compiler.py weight_image），尾列值无数值影响。
   c) tid 复用：a3 host_plan 的 in_graph 和编译器实际绑定的 p.a 可能指向
      不同 trace 记录（Python id() 复用撞名），按图名找不到融合段 A 输入；
      改按条目形状（kind=act_in 且 k==kp）定位。

   另一个容易误判的点：op=6 会读 Y_p 区的最后一列（常数列）在写入之前。
   这按构造无害——增广时该列随后被常数条纹覆盖，非增广时乘的是 W 零行。
   281 条 op6 全部核查过：未写格 100% 只出现在尾列。check_streams_a3 对
   这一形态记 INFO、其余列才算 ERR。

四、为什么只到 -8.8%：分杠杆对账 + 边界账虚高根因
------------------------------------------------------------------------------
拍数对账（校准口径，M 拍）：

  分量        a2        a3       变化        说明
  GEMM      336.43    336.44     ±0    GEMM 工作量不变（融合不减计算）
  STORE     276.41    218.67   -57.7 (-20.9%)   中间图 Y_p 不再落 DDR
  LOAD_CTX  226.35    184.09   -42.3 (-18.7%)   同上，少装一遍
  LOAD_W    103.62    106.64    +3.0 (+2.9%)    LUT 装载 + 融合段 pf 命中变差
  AE_ACTV     0         9.94   +9.9   新引擎开销（192 站共 281 条描述符）
  COPY       40.30     40.30    ±0    未动
  每段常数    3.46      3.23    -0.2   段数 2762 → 2580（-182）
  ----------------------------------------------------------
  合计      986.7     899.4   -87.3  (-8.8%)

字节对账：STORE 751.4 → 594.3MB（-157.1MB，-20.9%）；LOAD_CTX 837.6 →
680.3MB（-157.3MB，-18.8%）；weights blob +786,432B = 192 张 LUT × 4096B。

host 步对账：host_steps 1424 → 1242（-182）。actv 明细 GELU 24→3、
GELUActivation 12→1、SiLU 282→145、ReLU 13→0；norm 423 一步没动。

GEMM 占比 34.1% → 37.4%。要到 >50%，总拍得压到 672M 以下，还差 227M，
而剩余的 STORE 218.7M + LOAD_CTX 184.1M 大头在注意力链（q/k/v 图进
注意力算子的 COPY/装载），这轮范围（norm/actv 融合）碰不到。

边界账虚高的根因（boundary_account_a2.json 口径）：
  * 1612 个 PL→PL（无 host）边界按账面记了 408.9MB store + 393.9MB
    first-load，但其中绝大多数的消费者是注意力 lowering（A 经 COPY 进
    WRAM），不是普通 WGemm，融合机制根本套不上。
  * 真正「裸 GEMM → GEMM、中间只有重量化」的 S2 站点只有 10 个，已用
    恒等 LUT 折进融合对里。
  * norm 0 站的结构性统计（host_steps 口径 423 步；其中 411 个在编译
    节点序列里有独立节点，按节点序统计，2026-08-31 20:05 核完）：
      前邻是注意力          190   （norm 吃注意力输出，p 不是 GEMM）
      前邻是 host 算子       98   （残差加/窗口重排等）
      形状不配               60   （全是 AdaRMS：逐 token 缩放，p.n≠c.k）
      后邻是 host 算子       36
      后邻是注意力           17
      c 增广（NORM 约束禁）  10
      结构候选                0
    这个模型的 norm 长在注意力和残差旁边，不是 [GEMM→norm→GEMM] 夹心；
    即使是夹心的 10 处也撞了「NORM 要求 c 非增广」的引擎约束
    （全流 1183 个 GEMM 层里 984 个是增广）。

  推论：想继续压拍，下一步的杠杆不在融合，而在注意力链的数据供给
  （rotary/softmax_prep/COPY 侧），那是另一轮的范围。


五、机制速记（给下一轮接手的人）
------------------------------------------------------------------------------
* 融合对交错 lowering（_lower_fused_pair）：行 tile 外层；tile 内
  LOAD A_p → p 列组 GEMM（Y_p 按步长 pitch=kd+1 直写 CTX）→ 一条 op=6
  ACTV 原地查表 →（c 增广时）常数条纹写尾列 → Y_c 尾数预清零（m%16 时）
  → c 列组 GEMM（A=Y_p 直读，k=pitch）→ STORE Y_c。
  p 的 Y 不过 DDR，c 的 A 不从 DDR 装载。
* LUT 位精确：torch 运算序列与 host_driver 完全相同（fp32×so → 模块
  前向 → clamp(round/sa) 四舍六入五成双）。字节序是关键坑：lut 按
  x=-128..127 序生成，引擎按「字节值」寻址，铺映像前必须
  lut[128:]+lut[:128] 重排。修后 host 仿真 vs LUT 逐位 0/1966080。
* 表投递：LUT 字节附加进 weights_blob.bin（key='lut:{p}->{c}'），段内
  发一条 LOAD CTX 装进 256 字 CTX 区；16 lane 复制的字节图经 LOAD CTX
  路由字节 b → ctx[b%16, b_base+b//16] 落位。
* tid = Python id() 会复用：未入 trace 的算子（残差加等）容易撞死张量
  的 id。判别靠 in/out 形状核对 + 时间序（段属节点 seq>c 且就近生产者
  ==p 才算真消费者）。a2 驱动本身也是靠执行时间序区分同名 t<tid> 槽。
* 引擎拍数：ACTV T = 260 + ceil(m/16)×(n+3)。192 站共 9.94M 拍，只占总
  账 1.1% —— 引擎便宜，瓶颈不在它。
* NORM 路径（_op6_norm、_build_norm_image、norm_gold 引入）是死路径：
  本流 0 站，代码保留但未在真实站点上执行过。spec v1.1 的 z_max/sa_out
  约定（引擎代理 2026-08-31 通知）对已编译站点无影响。
