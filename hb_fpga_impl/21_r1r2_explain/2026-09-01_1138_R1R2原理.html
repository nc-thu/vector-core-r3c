R1（独立写通道）和 R2（CTX 预取）是怎么把 899M 拍压到 427M 的

生成时刻：2026-09-01 11:38:00　|　两项均已 RTL 落地并硬件实证（2026-08-31 设计，2026-09-01 Verilator 位精确门全过）　|　RTL：14_rtl_r1r2/rtl/（ae_dma.sv / ae_core.sv / ae_sched.sv）

零、先建立一个图景

加速器干活只有三类事：算（GEMM 阵列、softmax、激活引擎）、读（从 DDR 把权重和激活搬进片上）、写（把结果写回 DDR）。搬数据的是 DMA——一个专门搬数据的部件，CPU 只需要告诉它"从哪搬到哪"，它自己完成剩下的。

改造前的旧 DMA 只有一条"单车道"：读和写共用一个状态机。它先放下手里的写、去读一批，读完再写——什么并发都没有。所以旧总时间是三件事的串行和：算 387M 拍 + 读 292M 拍 + 写 218M 拍 ≈ 899M 拍（4.54ms）。

R1 和 R2 各解开一个死结：

R1（独立写通道）：把"写"从单车道里拆出来。读和算干完各自的事就算结束，写自己在旁边慢慢流——只要最慢的一条车道不超过"算"的 387M 拍，写就完全免费。

R2（CTX 预取）：把"读激活"藏进"算"的空档。GEMM 正在算这一段的时候，DMA 就提前把下一段要的激活搬进来。等下一段真正开始时，数据已经在片上等着了。

两招一起上：总时间从"算+读+写"的串行和，变成三条车道的最大值 + 一点依赖停顿 = 427M 拍（2.15ms），GEMM 计算占总时间 78.9%——"算"第一次成为绝对主线。

一、R1 独立写通道：具体怎么拆的

1.1 改造前的问题

旧 ae_dma.sv 是一个状态机服务所有请求。STORE（把结果写回 DDR）执行时，整条 DMA 都在等它：AW 地址握手 → W 数据 → B 响应，走完才轮到下一条 LOAD。而 STORE 的量不小——全帧 593MB、218M 拍，占总时间 24%。这段时间里 GEMM 阵列是闲的。

1.2 改造后

把一个状态机拆成两个独立引擎（[ae_dma.sv](../14_rtl_r1r2/rtl/ae_dma.sv)）：

读引擎（rd_st）写引擎（wr_st）
走的 AXI 通道AR（发读地址）→ R（收数据）AW（发写地址）→ W（给数据）→ B（收响应）
干什么LOAD_CTX / LOAD_W / 后台预取，数据写进片上 CTX/WRAMSTORE，数据从 CTX 读出写进 DDR
状态机R_IDLE→R_AR→R_R→R_R2→R_FINW_IDLE→W_AW→W_RD→W_WD2→W_W→W_B→W_FIN

AXI 总线本身就是全双工的——读地址/读数据 和 写地址/写数据/写响应 是物理上独立的两套线，以前只是没人用。拆开后 STORE 和 GEMM 真并发：Verilator 实测里能直接看到，seg_0600 段 STORE 与计算重叠了 2026 拍（占该段 45.5%）。

1.3 正确性：谁先谁后不能乱

并发最大的坑是抢资源。写引擎要从 CTX 读数据出去，而 CTX 只有一个读口（A 口），GEMM 喂数也要用 A 口。规则定成：GEMM 永远优先——写引擎在 W_RD/W_RD2 状态发现 GEMM 占着 A 口，就地停拍等它让出，绝不读到错的数据。调度器那边配合改一条：STORE 描述符发射后不再等完成（fire-and-forget），直接推进到下一条；LOAD 保持阻塞语义不变。

二、R2 CTX 预取：具体怎么藏的

2.1 改造前的问题

每段开始前要先花一大笔时间装激活（LOAD_CTX，全帧 680MB、184M 拍，占 20%）。这段时间 GEMM 阵列完全闲着——数据没到，算不了。

2.2 改造后

调度器里本来就有一个预取状态机（pf FSM），以前只认得一种任务：趁 GEMM 算着的时候，提前把下一段的权重装进 WRAM。R2 做的事：

  1. 预取标签从 1 种扩到 2 种（ae_sched.sv 的 pf_issue_ok 接受 TAG_W 和 TAG_CTX）——预取状态机现在也认得"下一段的激活"了。
  2. CTX 本身有空间可放：CTX 是 2MB 的片上存储，激活图按半区轮换使用（bit11 是半区标志），当前段用 A 半区时，预取的数据写进 B 半区，互不踩踏。
  3. 时机的关键判断：CTX 只有一个写口（B 口），GEMM 算完往外写结果也走 B 口。但 GEMM 只有在最后写回阶段（S_WB/S_WBTR）才碰 B 口，喂数的几十到几百拍里 B 口是空的——预取就专挑这个空档写。GEMM 进入写回时，预取暂停让位。

2.3 踩过的坑（如实交代，2026-09-01 修复）

R2 上线后在一段特殊的测试上翻过车：k=257 的长 GEMM 段开预取时，输出有 83 个字节差 ±1。排查发现预取写 CTX 时如果撞上引擎用写口，这次写会被静默丢掉——而 DMA 读引擎不知道，照常报"预取完成"，调度器以为数据到位，后面的计算就用了残缺数据。修法是加一个握手（pf_ctx_stall）：预取的写落不了地时，DMA 就地停拍等待，写一个不丢。修复后该段全 DDR 逐位一致，且预取照常省拍（净省 2,256 拍，−4.2%）。这个 bug 只在长 GEMM 段出现，因为喂入窗口长、预取撞上写口的概率才够高——短段一直测不出来。

逐段实测（Verilator，位精确 + 拍数都有）：seg_0600 省 548 拍（−18.4%）、seg_0602 省 2256 拍（−4.2%）、seg_0529 省 0 拍（撞了半区边界，按设计就该如此）。段与段有差异是正常的——预取有没有空档、写通道有没有撞车，取决于每段自己的形状。

资源代价：全芯片 LUT 只涨了 28 个（134,734→134,762；DMA 双引擎加的 774 个 LUT 被别处的综合优化抵掉了），DSP 1,728 不变（满片），时序达标（WNS −1.038ns @250MHz）。一拍不花的代价换一半时间——这是当时决定先做 R1/R2 而不是别的的原因。

四、为什么 R1 必须配 R2（单独一个都不行）

只做 R1（写藏进计算）：总时间 = max(算 387, 读 292) + 写被藏 = 46.8% 的 GEMM 占比，没过 50% 线——因为读还是串行挡在计算前面。

只做 R2（读藏进计算）：写回还堵着——写口和预取写抢同一个 CTX B 口，时序上互相牵制，模型上也不成立。

两个一起做，三条车道才真正各走各的：max(算 387, 读 292, 写 218) = 387，这就是 427M（387 + 40M 依赖停顿）的来历。

五、剩下的时间花在哪（衔接下一轮）

427M 里的构成：GEMM 336.4（78.9%）+ COPY 40.3（9.4%）+ AE_ACTV 10.0（2.3%）+ 依赖停顿 40（9.4%）。读写已经全部藏在计算背后（读 292 < 387、写 218 < 387，都不露头）。所以下一步只能压计算本身——这就是 R3 行组流水（GEMM 336→185M，见 18_r3_plan）和它之后的读压缩（见 20_read_compress）的由来。
